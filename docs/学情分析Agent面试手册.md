# 学情分析与报告生成 Agent 面试手册

2026 年 10 月更新：新增两份实际 LMS 文件适配，结构化记录全保留、可选模型原文摘录与截断恢复。大文件统计/指定学生/摘录路径分别压缩 17.02/16.39/14.69 倍（o200k），一次指定学生对照为原文 6/14、压缩 14/14、等预算截断 1/14；小文件未触发压缩，透传回答为 11/14。当前共 73 项自动测试通过。详见[业务评测报告](business-evaluation-2026-10-12.md)与[完整流程](pipeline.md)。这些结果与下文历史 349 条查询、合成实验分别表述。

这份手册用于准备项目介绍、技术追问、业务数据追问与效果评测追问。建议先练熟第 2 章的项目介绍，再用第 6 至第 9 章检查自己能否解释数据口径，最后按第 13 章进行连续模拟面试。

项目的核心表达是：面向教师，把自然语言需求连接到 LMS 业务数据，并在工具结果进入最终模型前，用程序化统计与必要证据选择减少上下文占用。真正需要讲清楚的是个人职责、统计总体、保留与省略的边界，以及效果数字如何产生。

## 1 面试前先统一事实口径

### 1.1 三类材料应分开准备

| 内容 | 当前性质 | 面试使用方式 |
| --- | --- | --- |
| 协作开发教师学情 Agent，组织 15 项业务能力，支持问答、报告和机构技能 | 参与 Agent 全流程业务 | 按需求、技能、工具、数据处理、问答与报告逐环节准备实例；不要将 15 项能力说成 15 个模型或 15 个接口 |
| EduContext 压缩模块、接口、保护规则、预算处理与测试 | 可由代码和记录核对 | 可以按本文技术回答展开，并现场定位实现 |
| 349 条真实查询、75% 到 97% | 已确认有实际评测记录，按字段计算正确率 | 基线为原始数据分批让模型压缩后再合成；面试前整理字段分子分母、金标和模型设置 |
| 约 28 至 30 倍压缩 | 已有合成数据实验支持的特定任务结果 | 不能自动归属于 349 条真实查询；若真实集也有此结果，应另出统计 |

真实业务评测：349 条查询，以“分批模型压缩再合成”为基线，字段正确率从 75% 提升至 97%。这是主要业务效果口径。字段总数、各类字段占比和模型设置需要从实际记录中整理，不从百分比倒推。

本地补充实验：720 条考试记录、120 名学生、2 个班级、6 次考试，以及 3 个模型任务。完整输入和压缩输入各答对 21/21 个要求事实，截断输入答对 3/21。两组实验的基线和用途不同，应分别表述；约 28 至 30 倍的本地结果也不能未经核对直接归入真实评测。

### 1.2 必须补齐的项目事实卡

面试前填写：项目周期【填写】；团队构成【填写】；个人负责的技能名称和数量【填写】；统一工具入口名称及协议【填写】；LMS 类型及部署方式【填写】；实际模型与上下文窗口【填写】；线上或离线环境【填写】；服务教师或机构规模【填写】；真实评测时间范围【填写】。

业务资料可以脱敏，但要保留结构和统计口径。无法确认的数据直接说明范围，不临场编造机构数量、并发量、日活、数据表规模或线上故障经历。

### 1.3 15 项能力应该如何准备

从真实技能文档逐项登记“技能名、触发意图、必要参数、业务接口、结果口径、错误处理、我的工作”。可能涉及班级概况、学生成绩、课程完成、出勤和机构报告，但这些只是整理方向，不是已经确认的 15 项清单。

至少熟悉三条真实链路：一个只需单工具的问答，一个需要多工具的学生分析，一个生成结构化报告的任务。每条准备一份脱敏输入、工具参数、返回片段和最终回答。

## 2 项目介绍与个人职责

### Q01 请用一分钟介绍项目

参考回答：我参与的是面向教师的学情分析与报告生成 Agent。教师用自然语言提出班级、学生或课程相关问题，Agent 根据业务技能说明选择工具，从 LMS 获取数据，再组织问答或报告。我重点做了工具结果进入最终模型前的上下文优化：针对大规模 JSON 中的重复字段和明细，先计算准确统计，再保留目标实体、异常和极值证据，最后做紧凑编码。模块用 Python 实现，核心不依赖额外模型调用。我的重点是让缩小后的输入仍能支持当前任务，并在必要内容超预算时明确告警。

职责补充：我参与了 Agent 全流程业务，包括业务能力组织、工具数据接入、问答与报告链路，以及上下文优化。全流程参与不等于独立完成所有底层组件；具体接口、框架和部署工作仍按实际协作分工说明。

效果补充：在 349 条超长真实查询上，相比原先分批让模型压缩再合成的方式，字段正确率从 75% 提升到 97%。这里是字段级指标，不是整条查询全对率。

### Q02 如果有三分钟，你怎么展开

第一分钟讲业务：教师要回答什么问题、原来需要手动整理哪些信息、Agent 如何拿到数据。第二分钟讲难点：工具返回的是结构化明细，直接截断可能切掉目标学生或改变统计分母；单纯让模型摘要也难以保证数字关系。第三分钟讲方案与证据：程序化全量聚合、任务保护、结构去重、预算失败处理，以及三路模型对照。结尾说明边界：不支持的分析算子保守保留，真实业务效果与合成实验分开汇报。

### Q03 你个人最有价值的工作是什么

参考回答：我参与了 Agent 全流程业务，因此能把教师的需求、技能规则、工具参数、数据口径和最终报告连起来理解。其中我重点展开的是上下文优化：设计原始 JSON 到压缩上下文的接口，区分字段角色，保护数值口径并记录证据来源。测试上分开检查程序完整性、token 计数和最终模型回答。讲全流程时，我会用一条真实请求说明各环节做了什么，再明确哪些工作由我完成、哪些与同学协作。

### Q04 这是研究还是工程项目

参考回答：它主要是工程项目。我调研已有上下文压缩和表格处理方法，选择适合业务约束的部分，做实现、消融和对照评测。贡献是将任务相关证据、确定性聚合、字段保护和预算退化组合成可接入模块，并验证其边界。我没有训练新的压缩模型，也不把它描述成已经发表的新算法。

## 3 Agent 的业务架构

### Q05 一次请求具体经过哪些环节

参考回答：教师提出需求后，Agent 先明确对象、时间、课程和指标口径，再根据技能说明选择工具并组织参数。LMS 返回的数据经过业务侧的权限和完整性检查，进入上下文压缩模块。模块返回上下文、大小、预算状态和统计信息，最终模型据此生成回答或报告。这里的权限、分页补全和参数解析属于外围链路；EduContext 本身接收的是已经获取的 JSON，不负责执行整个 Agent。

链路可记为：用户问题 → 业务技能与参数 → 统一工具入口 → LMS 数据 → 上下文压缩 → 最终回答或报告。

### Q06 为什么用技能文档和参考资料组织业务能力

参考回答：业务能力不仅是接口地址，还包括什么时候调用、参数怎么解释、数据单位是什么、异常状态如何处理，以及报告需要哪些章节。技能文档适合表达这些操作约束和业务口径，参考资料补充较长的定义与示例。实际工具负责执行查询。我的回答会结合真实技能文件说明内容结构，而不会把技能文档说成已经训练进模型的知识。

### Q07 统一工具入口有什么价值，会不会变成一个大杂烩

参考回答：统一入口可以统一参数结构、认证上下文、错误格式和结果包装，减少每项技能各自适配的工作。但各能力仍应有明确操作名与输入输出 schema，不能只接收任意字符串。建议按能力做参数校验和白名单路由，记录调用标识、分页状态和数据时间。是否已经实现这些机制，要以实际入口代码为准。

### Q08 业务能力数量与工具数量是什么关系

参考回答：二者通常不是一一对应。一个能力可能调用名单、成绩和课程多个接口；同一成绩工具也可能服务班级概况、学生异常和课程对比。15 项业务能力应该按用户意图及其执行规则计数，接口数量按真实工具定义计数。我会准备一张能力到工具的映射，避免面试时混用概念。

### Q09 问答和报告任务有什么区别

参考回答：问答通常围绕一个明确问题，优先给结论、口径和证据；报告有多个分析维度，需要章节结构、统计期间、数据范围和缺失说明。对于机构报告，还要明确跨班级汇总及机构隔离。压缩模块支持为当前任务提供数据，但并没有在自身内部实现报告模板系统、文件导出或机构权限系统。

### Q10 参数缺失或同名对象怎么办

参考回答：先用业务上下文补足可确定的参数；遇到重名学生、多个同名课程或不明确时间范围，应要求选择或澄清。不要让模型根据名字随意选一个人。上游应传稳定 ID，最好带机构范围。当前模块支持名称与 ID 的同类字段关联，但不是完整实体消歧系统，也不能单靠它解决跨机构同名和 ID 碰撞。

## 4 上下文压缩的设计

### Q11 为什么需要压缩，直接换长上下文模型不行吗

参考回答：长窗口可以容纳更多内容，但输入费用、处理耗时和模型从大量明细中计算的可靠性仍然需要考虑。我们已经拿到了结构化数据，可以先让程序完成确定性聚合，减少重复内容并让模型集中解释结果。换模型是外围选择，压缩模块提供另一种减少输入的方式；没有直接测量的成本或端到端时延收益，我不会给出百分比。

### Q12 为什么不用普通摘要或直接截断

参考回答：教学数据里的数字与学生、日期、课程、状态存在关联。普通摘要可能保留一个数字却丢掉分母或对应对象；前缀截断可能完整保留前几个学生，却删掉末尾目标学生。我先在全体输入记录上计算统计，再选择解释证据，并显式声明哪些逐行关系不能恢复。不能把这种任务压缩叫作全量无损压缩。

### Q13 模块接口如何接入现有系统

参考回答：核心接口是 compress(task, data, config, token_counter, force)，Python 实际调用中后四项为关键字参数。输入是原始需求与 JSON 值或 JSON 字符串，多工具可包装成工具名到结果的对象。输出 Result 包含 context、原始及压缩后大小、triggered、within_budget、target_tokens 和 stats。调用方先检查预算状态，再决定是否送入模型或拆分请求。

### Q14 为什么是 42 万字符，字符数等于 token 数吗

参考回答：420000 是业务给出的触发阈值，不是由 tokenizer 推导出的通用规律。默认严格大于阈值才压缩；等于阈值不触发。中文、英文、数字和 JSON 标点的 token 比例不同，所以不能把 42 万字符直接说成某个模型一定溢出。真实查询是否超窗口，应计入系统提示、用户问题、其他工具结果和输出预留，再用实际 tokenizer 判断。

### Q15 压缩预算如何算，未达标怎么办

参考回答：触发后目标是 min(200000, floor(原始 token 数/10))。先生成包含统计、证据和说明的候选，只移除可选代表行。必要内容仍超预算就返回 within_budget=False，不继续静默删事实。若候选反而比原文更耗 token，真实触发时直接返回完整原文。上游需要缩小查询、分拆任务或调整窗口；不能忽略失败标记继续硬塞。

### Q16 怎样理解用户任务，是否用了模型分类

参考回答：当前是轻量规则，识别报告、比较、异常等模式，配合显式字段角色和实体配置。对于排名、趋势、因果、加权、范围比较等没有实现的算子，回退到保守的全量结构编码。它没有通用语义解析器，关键词也可能误判，因此生产最好让上游提供明确参数。名字在问题中出现不等于已经准确解析了所有查询条件。

### Q17 字段重要性如何判断

参考回答：显式 schema 配置优先，其次用字段名规则识别实体、维度、度量、状态、时间与重要标记。未知且随行变化的字段、变化的嵌套单元格可能含有关键业务信息，会使该表全量保留。这样牺牲一些压缩率，避免不认识字段就丢掉它。不同工具同名异义应先规范化或分别处理，不能只靠字段名猜业务定义。

### Q18 为什么相同数据会有不同结果

参考回答：整体报告需要完整总体的统计和少量证据；指定学生分析需要该学生全部记录，因此明细保护集合不同。已有数据中，报告保留 5 条证据，S119 任务保留 10 条，其中包括他的全部 6 条记录。点名两个班级时，两班记录全部受保护，720 条都留下，所以只有约 6 倍压缩。

## 5 数值正确性与证据保护

### Q19 精确聚合是怎么实现的

参考回答：JSON 字符串中的小数用 Decimal 解析，累计统计用 Fraction 表示精确有理数。均值输出分子和分母，最后显示时再舍入。每个度量单独记录数值数量、缺失、null 和非数值数量。布尔值不算 0/1，字符串“80”不自动转成数字。如果上游已经把原始高精度小数转成 float，模块无法恢复之前丢失的精度。

### Q20 必须保留哪些原始行

参考回答：命中目标实体的所有行、异常状态行、配置阈值越界行、重要标记行、度量缺失或非数值行，以及首行和各度量极值见证都属于保护内容。极值并列时保留一条见证和并列数量，不意味着保留所有并列对象。少量前序代表行只是可选示例，不参与统计估计。

### Q21 你能保证每一个关键字段都不丢吗

参考回答：我会说明保证的范围。保留证据行的单元格值可以还原，实体目录保留观察到的实体关联，聚合在声明总体内准确。但被省略普通行的“学生、日期、分数、状态”完整联合关系不能重建，状态频次也不能替代逐行关联。如果任务要这些关系，必须保留相关明细或采用全量模式。当前自然语言规则也不能证明识别了所有隐含需求。

### Q22 多个选择条件是 AND 还是 OR

参考回答：模块的选择器用于证据保护，采用 OR 并集，不是完整 SQL 过滤器。比如“甲班的 S001”，同时命中班级和学生时，保护集合可能覆盖更多行；target_summary 也明确说明是并集统计。不能把它当成“甲班 AND S001”的答案。真正的交集、时间范围和排除条件应由上游查询或确定性算子处理。

### Q23 怎么去掉重复 JSON key 而不混淆数据

参考回答：表格编码用 columns 表示列顺序、rows 存单元格；全行共有的值提到 common，重复字符串在确实节省时用列字典。只对明确声明的字典列解释索引，成绩数值本身不编码。缺失字段的位置单独记录，避免与 null 混在一起。该设计减少的是表示冗余，不会因为两行相似就自动删除重复业务记录。

### Q24 可追溯编码和哈希能证明什么

参考回答：表路径和原始行号可以定位证据，输入 SHA-256 用来判断是否对应同一份原始数据。它方便复核某次回答用了哪一版输入。哈希并不能证明数据来自可信机构，也不是数字签名，更不能从摘要恢复原始记录。生产若需要回查，要由外围系统保存有权限控制的数据快照与请求标识。

### Q25 模块有没有发现所有异常

参考回答：没有。它保护明确异常状态、配置边界之外的值和极值见证，不等于完整异常检测。例如学生从 95 降到 70，仍在合法分数区间，但可能存在学习变化；当前没有实现这种时序检测。异常枚举也必须与业务核对，“未通过”可能是正常考试结果而非数据错误。是否排除异常参与均值，是另一个口径问题。

## 6 真实业务数据的高频追问

### Q26 你的数据里一行到底代表什么

参考回答：一定先定义数据粒度。已有合成实验中，一行是一名学生的一次考试记录，不是一名学生。真实业务还可能是题目作答、一次提交、课程学习事件或班级汇总。只有粒度确定，才能判断 count 是记录数还是人数，以及哪些字段可以相加。不能把同一个学生的多次考试当成多个学生。

### Q27 缺考、零分、null 和字段不存在怎么处理

参考回答：零分是明确的数值；null 表示接口明确给了空值；字段不存在可能是版本差异或未提供；缺考是业务状态，不能自动等同零分。当前模块将有效数值用于均值，并报告其他类型数量。真实业务若规定缺考按零分计入课程成绩，应该由明确的指标算子执行，并在结果里展示该规则，不能在压缩时偷偷填零。

### Q28 补考、重考和重复记录如何处理

参考回答：需要确认是按每次考试、首次成绩、最近一次还是最高成绩统计。重复接口返回可以依据稳定业务主键及版本去重，但两次真实考试不能因学生和课程相同而合并。当前模块不自动去重，不挑补考版本。上游应提供 exam_id、attempt_id、更新时间等语义；缺少这些字段就不能自信地还原业务事实。

### Q29 不同课程满分不同，能直接比较均值吗

参考回答：不能直接把 90/100 与 120/150 当成同一量表的绝对分数比较。可以按已确定规则转换得分率，但还需说明课程难度和考核目标不同，得分率也不自动代表同等学习水平。当前模块不会自行归一化，也不默认满分为 100；bounds 只是配置边界，不是归一化算子。

### Q30 平均分和及格率怎么算才可靠

参考回答：先确定统计总体、有效记录与权重。记录均值是成绩总和除以有效数值记录数；学生均值可能先算每人均值再平均，二者不同。总体及格率要用及格人数或次数除以对应有效分母，不能直接平均各班百分比。现有模块提供描述统计，没有实现通用及格率和加权指标引擎，相关业务计算应前置或另加明确算子。

### Q31 LMS 返回的只是第一页怎么办

参考回答：压缩只能保证对收到的数据统计正确，无法凭空发现所有未返回记录。上游要检查 total、页码或游标、has_more、分页失败及快照一致性。如果只拿到第一页，应明确返回数据不完整，不把第一页均值称为全班均值。外层分页元数据被保留，并不等于已经完成分页校验和补全。

### Q32 学生转班和名单变化怎么办

参考回答：要确认问题按当前班级还是考试发生时的班级归属统计。使用当前名单连接历史成绩，可能把学生过去的成绩错计到新班。正确处理需要有效期或事件时点上的班级关系。现有名称到 ID 关联不包含时态数据库能力，因此这种口径必须由业务查询明确提供，模块不会自动修复。

### Q33 多个工具数据互相矛盾怎么办

参考回答：分别保留来源、更新时间与筛选条件，检查是否一个接口返回最新成绩，另一个仍是旧快照。若无法判断权威版本，就标出冲突并限制结论。不能简单把工具结果拼接后当成新增记录，也不能自动用最后出现的值覆盖。当前模块各表独立统计，不跨工具自动 join 或去重。

### Q34 数据量到底多大，为什么只有几百行也会超长

参考回答：行数不是唯一因素。每行可能带课程说明、作业文本、嵌套题目、冗余名称或重复元数据。已有测试的 720 行达到 429210 字符，主要因为故意重复了学校说明，这是高冗余合成数据。真实项目应给出返回字符数、实际 token 数、行数、字段宽度和文本占比的分布，不能用这份合成规模代替真实 LMS 规模。

## 7 可现场推演的业务案例

以下均为练习案例，用来展示口径判断，不代表已发生的真实业务。

### 案例一 缺考与实际零分

同一场考试：S01 得 80 分，S02 得 90 分，S03 为 null 且状态缺考，S04 得 0 分且状态正常。

问：平均分、参考人数和缺考人数是多少？

回答：如果统计“有数值的考试记录”，总分 170，分母 3，均值约 56.67，缺考状态 1 条。若业务定义“应考四人且缺考按零分”，则均值 42.5，这是另一项指标。实际参考人数不能只靠非空分数普遍推断，还应核对考试状态和应考名单。最重要的是先报口径，不要只报一个平均分。

### 案例二 按记录平均与按学生平均

S01 两次成绩为 100、100；S02 一次为 50。按记录均值是 250/3，约 83.33；先算每人均值再平均是 (100+50)/2=75。

问：哪个结果正确？

回答：两者分别回答不同问题。分析所有考试记录的平均表现用前者；希望每名学生权重相同用后者。需要在指标定义中指定。当前默认记录统计不能直接命名为学生平均水平。

### 案例三 两个班的比例不能直接平均

甲班 10 人中 9 人及格，乙班 90 人中 45 人及格。两班及格率分别为 90% 和 50%，总体为 54/100=54%，不是 (90%+50%)/2=70%。

问：语义层思路在这里有什么用？

回答：保留分子、分母和粒度，而不是只保留百分比。跨组汇总先汇总可加的量，再计算比率。当前模块借鉴的是这种口径意识，没有实现完整语义层产品。

### 案例四 指定学生的异常证据

已验证合成学生 S119 六次成绩为 88、89、90、87、25、91，对应 1 月至 6 月各月 15 日，其中 5 月 15 日的 25 分被标记异常。

问：压缩后能否解释为什么下降？

回答：可以报告已有异常标记和日期、分数，也可以说明与其他记录不同；不能凭这些成绩断言是缺课、家庭原因或教学质量下降。要解释原因，还需授权查询出勤、作业等相关证据，并区分相关性与因果。当前模块没有因果分析能力。

### 案例五 跨机构 ID 重复

机构 A 和机构 B 都有 student_id=001。问“分析机构 A 的 001”时，如果上游去掉机构信息再合并，两个人可能被错误关联。

回答：首先由认证和查询限制机构范围，必要时使用 institution_id 与 student_id 的组合身份。不能把机构条件与学生条件直接放进当前 OR 保护选择器，就声称实现了 AND 过滤和权限隔离。保护了更多行并不意味着安全，这个问题必须在上游解决。

## 8 效果数字与评测设计

### Q35 349 条查询是怎么选出来的

参考回答：我们有 349 条超长真实查询的评测记录，基线是分批模型压缩后再合成。它们来自【实际时间范围与业务环境】，按【实际窗口判断与去重规则】形成评测集。这里需要从记录补齐任务类别分布和输入规模，不能把后续建议的分层方法说成当时已经采用。

必须准备原始计数。349 条应说明是请求、去重意图还是任务样本；不能把同一个模板的重复请求当成独立场景。还要解释失败请求是否计入、是否按结果挑选样本，以及调参集和最终评测集是否分开。

面试携带一张脱敏汇总表即可解释样本来源，不必公开原始学生数据。未填写的时间范围和分布应在面试前从已有记录补齐。

### Q36 75% 和 97% 的分母是什么

参考回答：这里统计的是字段正确率，不是 349 条查询中有 97% 全部答对。每个需要回答的字段与金标比较，再按实际评分脚本汇总。若汇总所有正确字段除以字段总数，是微平均；如果先算各题字段比例再平均，是宏平均，需要按实际实现确认。单位、分母和筛选条件是否单列字段，也要说明。

不要用 349×75% 去倒推出确定的正确条数，因为百分比可能经过舍入，也可能根本不是查询级指标。必须拿出实际分子和分母。

### Q37 75% 到 97% 提升了多少

回答：在同一指标、同一评测集的前提下，绝对提升是 22 个百分点；相对正确率提升约为 29.3%；错误率从 25% 到 3%，相对下降 88%。简历最好写“提升 22 个百分点”，并给出基线，避免“提升 22%”的歧义。这只是数学解释，不能替代真实评测记录。

### Q38 优化前的基线到底是什么

参考回答：真实业务基线是把原始数据分批交给模型压缩，再把各批压缩结果合成，用于完成任务。它比直接截断更强，但每一批都可能丢失 ID、时间、分母或跨批关系，合成阶段也难以恢复已经丢掉的事实。新方案将可确定的聚合移到程序中，按任务保留证据，再让最终模型解释。具体分批大小、是否行对齐、合成是否单独调用模型，应按原系统配置说明，不能臆定。

本地补充实验另设完整输入与前缀截断作为对照，不是 349 条业务评测的基线。两组结果应分别展示。

### Q39 为什么能保证提升来自压缩模块

参考回答：真实业务比较的是两条上下文构造链路。要检查是否使用同一批冻结问题和数据、同一最终回答模型与评分规则，并记录批量压缩模型的配置。如果这些条件不同，就需要解释差异，不能把全部收益归给某一个子策略。结构去重与任务证据选择可以进一步消融。已有本地小样本只能补充说明与完整输入持平、优于截断，不能代替对真实批量摘要基线的控制实验。

### Q40 谁来打分，金标如何生成

参考回答：确定性的数值可由独立程序按冻结口径计算，标识、日期和状态由原始记录核对。开放式报告需制定事实准确、口径一致、证据覆盖和不支持推断等评分标准，必要时双人标注和仲裁。现有实验使用独立金标逐字段评分，数值绝对误差容差为 0.00001，数组长度和顺序要求一致；没有完成真实业务双人标注，不应说已经做过。

### Q41 97% 之外的错误是什么

参考回答：97% 是字段正确率，剩余约 3% 是未判对字段，不能说成只有 3% 的查询失败。我会从真实评分记录选两例，解释它们属于上游数据、任务解析、关系丢失、模型读取、单位或输出格式哪类问题。一个分类可以对应多种原因，不能为了凑满 3% 编造案例。改进措施应对应已观察错误，例如范围问题前置过滤或增加明确指标算子。

### Q42 这么多指标，最重要的是哪个

参考回答：先看最终任务是否答对，再看必要事实是否保留以及统计是否准确，最后看压缩和耗时。程序统计全对不保证模型读取全对；模型某题答对也不证明所有普通明细都被保存。因此要分别报告正确率、信息保护、预算达标率和输入规模，不能用一个压缩倍数代表全部质量。

## 9 如何解释已有可复核结果

### Q43 本地实验具体做了什么

参考回答：使用同一份合成教学数据，设置整体报告、指定学生异常和两班比较三个任务。三组独立模型会话使用相同继承设置，分别接收原文、前缀截断或压缩结果，禁止代码代算和读取金标，作答后统一评分。输入分段完整传输并记录覆盖日志，避免读取工具的输出截断造成假对照。

限制：每组一次回答三题，原文共享读取；不是 9 次独立生产 API 调用。没有可核实的具体模型版本、服务端用量或采样参数，因此不能报告模型级可重复性已经完全解决。

### Q44 28 至 30 倍是什么统计量

参考回答：压缩倍数定义为原始上下文 tokens 除以压缩上下文 tokens。已验证的约 28 至 30 倍来自特定高冗余数据上的报告和指定学生任务，经 cl100k_base 与 o200k_base 两种公开编码复核。它不是所有查询的平均值或下限；也不包含模型输出。写“最高约 28–30 倍”不如说明“指定任务约 28–30 倍”清楚。

| 任务 | cl100k 原始到压缩 | 压缩倍数 | 十倍目标 |
| --- | --- | --- | --- |
| 整体报告 | 89326 到 3013 tokens | 29.65 倍 | 达到 |
| 指定学生 | 89326 到 3227 tokens | 27.68 倍 | 达到 |
| 两班比较 | 89326 到 14491 tokens | 6.16 倍 | 未达到 |

### Q45 两种 BPE 都验证了，是否就能证明模型不超限

参考回答：不能。它们是公开编码基准，能够发现字符启发式的偏差，但不一定等于生产模型 tokenizer。硬预算需要注入实际模型计数器，并预留系统消息、用户输入和生成空间。验证显示低冗余 6000 条数据在 cl100k 下约 10.04 倍，而 o200k 下约 9.94 倍，临界是否达标确实会变化。

### Q46 自动化测试到底测了什么

参考回答：历史交付记录中 38 项核心及完整性测试加 6 项评测器测试，共 44 项。其中一项随机化测试对 120 份结构数据跑三种模式，共 360 组检查，不能说成另外 360 个独立测试函数。验证包括 Decimal、超大 ID、missing 与 null、实体全量保护、分组口径、异常见证、预算失败和候选膨胀退化。它们验证程序性质，不属于 LLM 正确率。

### Q47 只做三题是不是太少

参考回答：是。它只证明最小链路可以跑通，并暴露了截断和保守保护的行为，不能支持生产准确率结论。下一步应加入真实任务分层、不同数据分布、多个模型及多次运行，特别是长文本、多工具冲突和复合条件。若有 349 条真实集，也应说明它如何补足这些覆盖，而不是单凭样本数宣称泛化可靠。

## 10 选型与工程边界

### Q48 为什么没有直接接 LLMLingua

参考回答：调研后认为本任务的首要风险是数值与业务对象、分母之间的关系。通用 token 选择压缩可以作为候选，但还需模型依赖与结构关系验证。这里先用标准库完成可核对的聚合和编码，部署成本更低。不能说 LLMLingua 完全不支持结构化数据；它已有相关能力，只是当前项目没有引入或做生产级对比。

### Q49 TAP4LLM 和 TOON 给了什么启发

参考回答：TAP4LLM 的表格选择、统计增强和打包思路，启发我把明细选择与可计算摘要分开；TOON 的紧凑结构表达启发了共享表头与避免重复字段。当前输出仍是自定义 JSON 协议，不宣称兼容 TOON，也没有复现论文里的完整系统或效果。面试重点是说清借鉴点与实际实现之间的关系。

### Q50 为什么不用向量检索或 RAG

参考回答：这一阶段已经拿到本次工具数据，问题是如何组织输入。相似度最高的记录不一定覆盖统计总体，按 top-k 检索会改变分母，还可能漏掉极端值。检索更适合另一些资料查询任务；对这里的数值聚合，应先保证总体完整。如果后续需要跨知识库找教学材料，可以在其他环节引入，不必为了压缩 JSON 先加向量库。

### Q51 为什么不直接在数据库里聚合

参考回答：如果可以控制数据库或 API，在源头按正确口径聚合、只返回必要列通常更有效。模块定位是处理既有多工具结果，尤其在接口无法立即调整时补足最后一段。两者可以配合：上游限制时间、对象和分页，模块减少跨工具表示冗余并保护证据。不能把客户端压缩包装成优于一切数据库聚合的方案。

### Q52 性能和复杂度如何回答

参考回答：核心做全量解析和多次遍历，大部分工作随记录数与字段数增长；高基数分组、实体目录和精确有理数也会增加开销，不能只用一句 O(n) 代表所有成本。历史合成基准在 Python 3.14.4、Windows 11 上，1 千、5 千、1 万行的三次热进程中位约为 0.13、0.64、1.28 秒，未测峰值内存，也不含模型时间。它不是流式引擎或生产吞吐承诺。

### Q53 异常输入和接口升级怎么处理

参考回答：触发解析时拒绝重复 JSON key、非有限数等会使事实解释不清的输入，并对非法配置或计数器结果报错。未知变动字段采取保守保留。需要注意，未触发时字符串原样透传，不执行 JSON 校验，因此输入校验仍应由上游负责。接口升级应维护字段契约与回归样本，不能指望关键词识别覆盖所有新 schema。

### Q54 安全和隐私如何保证

参考回答：权限校验、机构隔离、字段脱敏和审计应在业务工具和存储层执行。压缩模块保留实体和明细，本身不是脱敏器；哈希也不等于匿名化。学生评语可能包含伪指令，最终模型应将工具内容视为数据，不能据此更改任务或调用权限。这些是系统接入要求，当前模块没有实现完整安全治理，更不能因此声称符合某项法规认证。

### Q55 多轮追问怎么处理

参考回答：压缩结果只承诺支持当前任务，不能假定足以回答所有后续问题。用户从“整体均分”追问“某天某学生为什么下降”时，应该重新获取或从受控快照读取必要数据，按新任务重新压缩。若缓存，应关联数据版本、机构、权限、配置和任务条件。当前模块不管理会话记忆、缓存和数据留存。

## 11 困难改进与协作追问

### Q56 讲一个确实解决过的技术问题

参考回答：最初只看字符与启发式 token 估算，可能误判一些结构数据已经达到十倍目标。加入两种 BPE 审计后发现估算器对不同内容分布的偏差，调整了英文、数字、中文和标点的计数方式，并让班级比较正确显示预算失败。这个例子说明字符减少、token 减少和回答正确是三件事，必须分别验证。

### Q57 有没有失败的压缩案例

参考回答：有。目标覆盖全部两个班级时，必须保护 720 条明细，无法达到十倍；变化的教学评语需要全量保留时，只有约 1.53 倍；高基数分组可能导致统计目录比原文更大，此时回退完整原文。这些案例被保留在报告中。失败处理是功能的一部分，不能为了漂亮指标只展示高冗余输入。

### Q58 你会优先改进哪里

参考回答：优先让上游提供结构化任务参数和稳定字段定义，再增加少量高频业务算子，例如明确分母的及格率、补考规则、相对日期过滤。随后完善真实业务配对评测及精确 tokenizer 接入。只有在评语等长文本确实成为主要瓶颈、且业务允许有损处理时，才考虑模型压缩。上述是改进方向，不是现有模块已经支持的能力。

### Q59 如何证明不是只调用现成库

参考回答：我可以展示接口设计、保护规则、数值与缺失处理、表编码协议、预算退化以及独立测试。核心没有依赖压缩模型库，难点在业务关系和失败边界。但也不必强调代码全部从零才有价值；重要的是能解释每一步为什么做、哪些行为可以验证、为什么没有过度引入组件。

### Q60 协作开发中如何划分责任

参考回答模板：我负责【真实模块或技能】，与负责【真实相邻模块】的同学约定【实际接口】。我们用【真实联调方式】核对输入粒度、异常返回和输出 schema。遇到【实际问题】时，我完成【可核查改动】，其他同学完成【对应改动】。不要把假设中的规范、代码评审或线上灰度说成已经发生的团队过程。

### Q61 这个项目的业务价值是什么

参考回答：它把教师的问题连接到业务数据，并让报告中的统计有明确依据；我负责的模块减少了超长工具结果中的冗余，使模型能够在较小输入中读取统计与证据。业务价值可进一步用教师任务完成时间、人工修订量和报告事实错误衡量。如果没有真实用户研究，不说已经节省多少人力，也不把离线事实正确率等同教师满意度。

### Q62 原来已经做了分批压缩 为什么还会出错

参考回答：分批解决了单次输入过长，但没有自动解决信息完整性。某个学生的记录可能分布在多个批次，局部摘要只保留了部分时间点；某批只有平均分没有数量，合成时就无法正确加权；某批把低频异常当作不重要信息删掉，后面也恢复不了。这些是需要检查的失效机制，真实发生了哪一种，应从错误记录举例。我的方案让可计算统计覆盖完整输入，保护指定对象和异常证据，减少中间模型摘要决定保留什么的机会。

### Q63 你是不是只是把模型计算改成 Python 计算

参考回答：确定性计算前移是主要收益来源之一，但模块还解决了数据选择和表示问题。只有均值不足以支持学生异常分析，所以要保留目标学生明细；只保留几条明细又不能代表整体，所以必须保留完整总体统计；最后用结构编码减少重复，并对无法满足预算的情况显式失败。三个部分共同服务当前任务，而不只是替换一个求和函数。

### Q64 为什么不改进原来的分批摘要提示词

参考回答：可以改进，合理的强基线应该要求每批保留 sum、count、ID、时间、异常和来源，合成时再由程序合并。这样会接近结构化中间结果的设计，也应纳入后续对照。当前 75% 到 97% 只能表示相对实际旧链路的效果，不说明比所有改进后的分批算法都好。如果能控制上游，直接产生这些中间统计通常也比让模型反复从明细计算更可控。

### Q65 新旧方案的调用成本和耗时如何比较

参考回答：要比较完成一条查询的总成本，而不只比较最终上下文。基线包含各批压缩、合成及最终回答的实际调用；如果某两步合并在同一次调用中，就不能重复计数。新方案计入 Python 预处理和最终回答。统计所有调用的输入输出 tokens、重试、缓存及实际墙钟时间。批次并发时总 token 费用会相加，但延迟不是各批时长简单相加。我目前不会从“30 倍输入压缩”推出“成本或耗时下降 30 倍”。

### Q66 如何让面试官信服字段正确率的提升

参考回答：我会带一条脱敏样本，列出问题、原始证据、金标字段、旧链路最终字段、新链路最终字段及判分。例如一个字段是平均分，另一个是统计单位，二者分别判定；空答案和错误答案是否都计错，按实际评分规则解释。再给出整个 349 条集合的字段总数和正确数，说明宏平均或微平均。模型摘要中的字段很多，但评分必须围绕任务要求，不能因为新方案多输出容易的字段而稀释错误率。

## 12 简历表述与数字证据包

### 12.1 真实业务评测的主要写法

优化效果：在 349 条超出预设上下文窗口的真实查询上，相比分批模型压缩后再合成的基线，字段正确率由 75% 提升至 97%，提升 22 个百分点。

如果原评分包含关键事实字段和统计口径字段，可进一步写“关键事实及统计口径字段正确率”，但不要把字段级 97% 写成查询成功率。这里不混入尚未确认属于真实集的最高压缩倍数。

### 12.2 本地补充实验的写法

优化效果：在超过 42 万字符的合成教学数据上，报告及指定学生任务经两种 BPE 编码复核实现约 28 至 30 倍压缩；3 项模型对照任务的 21 个关键事实与完整输入同为全部正确，并通过 44 项自动化测试。

这段与当前可复核材料一致。若实际个人工作主要是协作联调，应相应调整“实现”与“参与实现”的措辞。

### 12.3 扩展效果数字时应补齐的统计

在【日期范围】的 349 条【去重规则】超长真实查询上，相比分批模型压缩后再合成，字段正确率由 75% 提升至 97%；输入 token 压缩中位数为【实际统计】，最高为【实际统计】，目标预算达标率为【实际统计】。

只有证据支持时才能填入。两种 BPE 编码可作为补充审计，但主结果应明确生产 tokenizer。不要把合成集的 28 至 30 倍直接填成真实集最高值。

### 12.4 评测证据包至少包含什么

每条记录建议保存：脱敏 query_id、任务类别、原始问题、输入快照标识与哈希、行数与数据粒度、原始及各变体 tokens、计数器、模型版本与设置、金标、答案、逐项评分、失败原因、预算是否达标。保存数据必须符合项目实际权限和留存要求。

汇总应提供：总样本数与排除原因、类别分布、微平均和宏平均或明确选择其中一种、正确率分子分母、压缩倍数中位数与分位数、达标率、错误分类。若要强调显著性，可对配对查询结果做合适的配对分析；单看两个四舍五入百分比不够。

## 13 连续模拟面试

### 第一轮 业务与职责

面试官：你们实际解决什么问题？ → 先回答教师的具体任务，再说 Agent 链路。

面试官：15 项能力有哪些？ → 取出真实清单，挑三条讲输入、工具和输出，不临时凑数。

面试官：你做了什么，别人做了什么？ → 用真实交付划分，不用“我们都做了”回避。

### 第二轮 数据口径

面试官：一行代表什么？ → 说明粒度。

面试官：一个学生考六次怎么算人数？ → 区分记录数和去重人数，说明当前模块没有默认去重。

面试官：缺考是零分吗？两个班比例怎么合并？ → 用第 7 章案例展示分母意识。

面试官：上游少返回一页，你的均值还准确吗？ → 对收到记录准确不等于对完整业务总体准确。

### 第三轮 技术与效果

面试官：保留了哪些行，删掉后还能回答新问题吗？ → 明确保护规则和任务范围。

面试官：30 倍是不是因为重复说明太多？ → 承认高冗余分布，补充低冗余与未达标案例。

面试官：349 条的 97% 怎么算？ → 明确字段正确率，说明分批模型压缩再合成的基线，再展示真实字段分母与金标。

面试官：为什么不在数据库里算？ → 承认源头聚合的优势，说明模块所处环节及约束。

面试官：下一步做什么？ → 给出与错误类型对应的改进优先级。

### 面试前二十分钟复习顺序

前五分钟练一分钟介绍与个人职责；接下来五分钟口算三个分母案例；再用五分钟核对所有数字的基线与来源；最后五分钟练两个失败案例和一个改进方向。能自然解释，比背诵术语更重要。
